# ClearBill Deployment and Acceptance

Status: both contracts are deployed and verified on Sepolia. The updated Render service passed shared-bill read-only API and mobile page checks. Shared-bill wallet transactions from the hosted origin and mobile MetaMask remain to be checked.

## Local chain

Follow the exact commands in the repository README. `npm run deploy:local` sends creation transactions from a disposable unlocked Hardhat account and writes `.local/deployment.json` and `.local/shared-deployment.json`. Set `SHARED_DEPLOYMENT_FILE=.local/shared-deployment.json` to enable shared bills on the local server. The server checks chain ID, creation receipts and runtime bytecode before serving the API. Local browser tests create additional transactions and reset no chain state, so bill IDs increase across runs.

For a fresh reproducible run, stop the old chain, start a new one, deploy again and restart the server. Delete only local browser state for this site's test origin if pending records refer to the old chain; the app will not reinterpret those records as valid new-chain transactions.

## Sepolia preparation

1. Prepare dedicated MetaMask test accounts and obtain Sepolia test ETH from a legitimate faucet. Never use real ETH or a mainnet key for the coursework demonstration.
2. Build the repository with `npm ci` and `npm run build`. Record the exact commit, compiler and optimizer settings.
3. Run `npm run serve:deployer` and open `http://127.0.0.1:3001` in a desktop browser with MetaMask. This separate tool binds to loopback only and serves the exact local compilation artifact. Check that it displays Sepolia and the intended wallet, then review MetaMask's contract-creation request and gas fee. The constructor takes no arguments. No private key enters the project or server.
4. After user approval, the tool waits for the mined creation receipt, compares deployed runtime code byte-for-byte with the local build and offers a public `sepolia.json` download. A submitted hash alone is not a verified deployment. If the page loses connection after submission, check that hash before any retry.
5. Put the downloaded file at `deployment/sepolia.json`. It contains only `chainId`, `contractAddress`, `deploymentBlock` and `deploymentTransactionHash`. There is intentionally no checked-in example address. Run `npm run verify:deployment` with a Sepolia RPC URL and that manifest.
6. Test the wallet connection and signing flow with real MetaMask, including one actual phone in the MetaMask browser. Capture genuine screenshots and receipt hashes in the evidence index. The same business methods have already been exercised on Sepolia using authorized test keys through a one-time CLI script; this does not establish MetaMask compatibility.

## Render web service

The public service is [clearbill-dapp.onrender.com](https://clearbill-dapp.onrender.com/). Render builds `main` with `npm ci --include=dev && npm run build && npm prune --omit=dev` and starts it with `npm run start`. Build-only tools are removed before runtime. The service uses the Free instance in Ohio. The recovery configuration uses `/healthz` for HTTP process liveness and retains `/api/v1/health` for strict blockchain readiness. Its environment sets `RPC_URL=https://0xrpc.io/sep`, `CHAIN_ID=11155111`, `DEPLOYMENT_FILE=deployment/sepolia.json` and `HISTORY_BLOCK_SPAN=10000`. The shared manifest defaults to `deployment/shared-sepolia.json` on Sepolia; `SHARED_DEPLOYMENT_FILE` can override it. The endpoint contains no private credential. Render supplies `PORT`; the service listens on that port.

The liveness endpoint only confirms that Express can respond; it does not claim that blockchain reads or payments are available. Startup and the readiness endpoint still validate deployment receipts, network and exact runtime code. A missing receipt is reported as `RPC_RECEIPT_UNAVAILABLE`; contradictory receipt data still fails deployment verification. The provider sends individual JSON-RPC requests with explicit JSON and application headers for public endpoint compatibility. Solidity files use LF line endings so Windows and Linux builds produce matching source metadata.

On 18 October 2026, PublicNode returned null for the original deployment receipt while Blockscout and alternative RPCs returned its successful receipt. The process repeatedly exited during startup. Before changing the endpoint, 0xRPC returned both matching deployment receipts and runtime code, Paid for ordinary bill 4 and shared bill 1, and confirmed for the recorded ordinary payment. This read-only check did not submit transactions. A public endpoint can still fail or rate-limit; a dedicated RPC account may be preferable for sustained usage.

The initial deployment built commit `e8f5692` and reached Render's Live state. The public `/api/v1/health` returned HTTP 200 and `ready`; `/api/v1/config` returned Sepolia and the verified contract address; bill 4 returned Paid; its history returned the creation and payment events in one complete page. Chrome displayed the hosted bill page and its timeline without a connected wallet. A wallet transaction from this HTTPS origin has not yet been tested. The free service can spin down when idle, and the site depends on the public RPC provider for chain reads.

After commit `e93518d` was pushed to `main`, the public service reported `ready` and returned the shared contract address in `/config`. Hosted shared bill 1 returned Paid, 0.0001 ETH paid and two payers; its history returned five events with `complete=true`, and the last payment receipt returned `confirmed` with one matching event. `/shared-bills/1` returned HTTP 200 and rendered at 390 CSS px in a read-only browser capture. The hosted wallet signing path has not yet been exercised.

## Evidence and recovery

Record chain, contract, wallet type, date, screenshot, transaction hash and result for each live test in `docs/evidence/INDEX.md`. The student can cite this evidence in the separately managed report. After a server restart, confirmed bills and history must still be reconstructable from the original contract.

The contract has no pause, upgrade or administrator. Taking the website offline does not disable direct contract calls. Replacing the contract creates a separate ledger and requires an explicit migration decision; do not silently point the UI at another address.
